# AGENTS.md

## Build & Run

**Supported paths:**

- **Docker (reference path; Windows/Linux/macOS):** `docker compose up --build` at the repo root. Requires a `Publicacoes_Prod` `.bak` in `Web.Blazor/wwwroot/Files/Backup/Database/` (the stack does not ship one and has no schema fallback). See the README Getting Started.
- **Windows + Visual Studio / IIS Express (Windows only):** opens `MediaOrganizerApp.sln`, starts both projects (API `https://localhost:44303`, UI `https://localhost:44327`). See README Getting Started.

`dotnet restore` / `dotnet build` alone are not a runnable path: both projects default to `https://localhost:5001` (port collision), `appsettings.json` points at the author's `DESKTOP-SLIMNUD\SQLEXPRESS`, and the Development `BaseUrl` points at the IIS Express port `https://localhost:44303`. `scripts/start-all.ps1` launches both with default profiles, so it hits the same collision.

```bash
dotnet restore MediaOrganizerApp.sln
dotnet build MediaOrganizerApp.sln
dotnet test MediaOrganizerApp.sln
```

## Deploy de producao (IIS local, self-hosted Windows)

`.github/workflows/main.yml` faz publish **self-contained** (`win-x64`, `PublishReadyToRun=false`) e deploy em IIS na mesma maquina. Topologia: **WebApi em HTTP `http://localhost:4100`** (loopback, accessed pelo Blazor no mesmo host) e **Blazor em HTTPS `https://localhost:4110`** com certificado auto-assinado. Pools/sites: `MediaOrganiserApi` -> `C:\inetpub\MediaOrganizerAPI`, `OrganiseIt` -> `C:\inetpub\OrganiseIt`. O `ASPNETCORE_ENVIRONMENT=Production` e posto explicitamente no app pool — sem isso o ramo de producao do pipeline nunca e aplicado.

- **Os nomes dos app pools tem de coincidir com os logins SQL**: em `Publicacoes_Prod` existem `IIS APPPOOL\MediaOrganiserApi` e `IIS APPPOOL\OrganiseIt` (ambos `db_owner`). Como `Trusted_Connection=True`, o processo corre com a identidade `IIS APPPOOL\<nome do pool>`; um pool com outro nome fica **sem acesso a base de dados**. Nao renomear sem criar o login SQL correspondente.
- SQL: instancia **`SQLEXPRESS`** com `TcpPort=1433` **estatica** — por isso `Server=DESKTOP-SLIMNUD\SQLEXPRESS` e `Server=DESKTOP-SLIMNUD,1433` resolvem para a mesma instancia. `MSSQLSERVER` e `DEVELOPER` existem mas estao parados.
- **`wwwroot\Files` esta versionado no git** e e uma mistura: `Pictures\Application|Authores|BookHardCovers` sao **assets da app** (icones, bandeiras) e `Uploads\` + `Backup\` sao **dados do utilizador** (~740 MB de publicacoes e um `PdfsAndCovers.zip` de 493 MB). O git e a fonte de verdadeira, por isso o `robocopy /MIR` e integral e **nao** exclui subpastas. Nao usar `/XD wwwroot\Files`: num destino limpo a app ficaria sem icones. O workflow faz antes backup de `wwwroot\Files` para `C:\NewProjects\Publish\_backup_uploads\Files-<timestamp>`. **`/XD` nao protege contra o purge do `/MIR`** (verificado em sandbox) — nao confiar nele para preservar dados.
- **HSTS esta desligado em producao** (`Hsts:Enabled = false` em `appsettings.Production.json`). Com certificado auto-assinado, o browser memoriza o HSTS e depois recusa a-certificado invalido sem forma de saltar. Ligar `Hsts:Enabled` apenas quando passar a usar um certificado de confianca.
- `DetailedErrors` e `UseDeveloperExceptionPage` ficam so em Development; a WebApi responde 500 em `application/problem+json` em producao.
- O workflow exige **elevacao** (IIS + `Cert:\LocalMachine\My`), por isso o runner self-hosted tem de correr como administrador.
- O `web.config` do publish usa `AspNetCoreModuleV2` com `hostingModel="inprocess"` e `processPath=".\Web.Blazor.exe"`: e preciso o **ASP.NET Core Hosting Bundle** instalado na maquina.
- O publish self-contained do Blazor da ~2,3 GB (runtime + locales + `wwwroot\Files`). Cada deploy copia esse volume com `/MIR`.
- **O pipeline verifica o resultado, nao confia no "Succeeded"**: o ultimo passo (`Smoke test (site API, Blazor e base de dados)`) faz `GET http://localhost:4100/api/dashboard/health` com o header `ApiKey` lido do `appsettings.Production.json` publicado (o `ApiKeyMiddleware` devolve 401 sem ele; o endpoint le a BD, por isso tambem valida a connection string) e `GET https://localhost:4110/` com validacao de certificado desligada. Aceita 2xx/3xx no Blazor, **200** na API, com retry ate 180 s (`Start-Sleep 5`). Em falha faz dump do corpo das respostas, do estado de pools/sites, de `netsh http show sslcert` e dos eventos IIS/WAS/HttpEvent e **falha o job** — antes, um 500.19 ou um TLS abortado passavam verdes. **A validacao do certificado e desligada com um delegate compilado (`Add-Type` → `TrustAllServerCertificate`), nunca com um ScriptBlock:** `[Net.ServicePointManager]::ServerCertificateValidationCallback = { $true }` e invocado na thread do handshake TLS, onde nao ha runspace, e rebenta com "There is no Runspace available to run scripts in this thread" — a ligacao e fechada **antes de o pedido chegar ao IIS**, o probe fica em `Blazor=0` nas 36 tentativas e o worker on-demand nunca arranca (foi a causa do run vermelho de 11/11/2026). Plano B: `curl.exe -k`.
- **Certificado HTTPS**: nao se usa `Set-WebBinding -PropertyName iisCertificateThumbprint` (essa propriedade nao existe no binding: ficava um endpoint 4110 sem certificado no HTTP.sys, handshake abortado + HttpEvent 15021). O passo "Deploy to IIS" faz `netsh http delete sslcert ipport=0.0.0.0:4110` (se existir) e `$httpsBinding.AddSslCertificate($cert.Thumbprint,'My')`, e **verifica** com `netsh http show sslcert` que o hash ficou registado — senao falha.
- **ACLs**: o passo "Deploy to IIS" (PASSO 2, antes do `robocopy /MIR`) garante `icacls <pasta> /grant "IIS APPPOOL\<pool>:(OI)(CI)M"` nas duas pastas de destino (idempotente, sem `/T`) e **confirma que a ACE ficou aplicada** (`icacls` de novo, falha se nao aparecer). Sem esta ACE a identidade do pool nao escreve em `wwwroot\Files`; `C:\inetpub\MediaOrganizerAPI` e `C:\inetpub\OrganiseIt` so tinham as ACEs herdadas de `C:\inetpub` (`Admin`/`System`/`Utilizadores`), sem `IIS_IUSRS`. **Nota:** a ausencia desta ACE nao explica sozinha o `500.19` observado — o mesmo erro afecta `C:\inetpub\wwwroot\LLMLocalCloudArena` (site que ja tinha `IIS APPPOOL\LLMLocalCloudArena:(OI)(CI)(M)`), portanto ha tambem um problema de IIS/host a diagnosticar (ver bullet seguinte).
- **Aviso 2303 (W3SVC-WP, `0x80070002`)**: e o preload/auto-start do IIS a tentar arrancar a app sem que a pasta esteja completa; nao vem do workflow. O pipeline fixa `startMode=OnDemand` + `autoStart=true` nos pools e `preloadEnabled=false` nas apps (`appcmd set app "<site>/" /preloadEnabled:false`) para o arranque ser on-demand e deterministico. `startMode=AlwaysRunning` volta a exponenciar o aviso.
- `ASPNETCORE_ENVIRONMENT=Production` e posto no app pool **preservando as `environmentVariables` existentes** (le a colecao, remove so a chave e volta a escrever); a atribuicao direta de um hashtable apagava as restantes. O passo valida no fim que o valor ficou `Production`.
- Os **access logs de IIS** sao ligados (`logFile.enabled=true`) nos dois sites; estavam desligados desde setembro, por isso os 500.x nao deixavam rasto. `Start-WebAppPool`/`Start-Website` so correm se o estado nao for `Started` e o estado final e validado (falha se nao ficar `Started`).

## Docker local (opcional, Linux containers)

`docker-compose.yml` (raiz) sobe `sql` + `db-init` + `ollama` + `webapi` + `webblazor` e **nao** substitui o deploy IIS. Correr na raiz do repo (nao dentro de `docker/`): `docker compose up --build`.

- Portas publicadas: `5000` (WebApi) e `5001` (Blazor). `sql` e `ollama` **nao** publicam portas (o host ja usa 1433/11434); aceder via `docker exec`.
- `db-init` (`docker/init-db.sh`) espera pelo SQL, restaura o `.bak` de `SQL_BACKUP_FILE` (default `28102026_123256.Bak`, lido de `Web.Blazor\wwwroot\Files\Backup\Database`) com `MOVE` para `/var/opt/mssql/data`, e normaliza `ApplicationSettings` para o contentor: `\`→`/` nos caminhos (`Pasta*`) e `ModelBaseUrl=http://ollama:11434`, `ApiBaseUrl_Production=http://webapi:5000`, `FileManagerApiBaseUrl_Production=http://webapi:5000/api/FileManager`. E idempotente (se a BD existir, so reaplica os settings).
- **Acesso a dados nos contentores:** `Application/Factories/ConnectionManager.cs` (usado por ~121 call sites em 19 ficheiros, ex. `BaseRepository.GetCount()`) deixou de reconstruir a configuração só a partir de `appsettings.json`. Cada host chama `ConnectionManager.Configure(builder.Configuration)` no arranque (`MediaOrganizerApp.WebApi/Program.cs` e `Web.Blazor/Program.cs`), pelo que as env vars (`ConnectionStrings__SqlServerCon`) e o `appsettings.Production.json` passam a ser respeitados. Sem `Configure` mantém-se o comportamento antigo (fallback), o que preserva `PromptEditor`/testes. Era esta a causa do dashboard vazio no Docker: `DashboardController` → `GetCount()` → `ConnectionManager` tentava `DESKTOP-SLIMNUD\SQLEXPRESS` dentro do contentor.
- **Caminhos de imagens (`\` vs `/`):** `WebPathHelper` (`Web.Blazor/Services/Common/WebPathHelper.cs`) normaliza `ImagemCapa`/`DigitalPath`/`CoverFile` ao resolver o caminho físico (`File.Exists`) e o URL (`<img src>`). O `db-init.sh` também faz `REPLACE('\','/')` em `Publicacao.ImagemCapa`/`DigitalPath`, `Autor.ImagemAutor` e `Media.FilePath`/`FileUrl`/`CoverFile` (guards `COL_LENGTH`, idempotente). Sem isto as grids mostram o ícone "sem imagem" em Linux.
- **Dashboard (`Index.razor`):** cada pie chart tem o seu próprio `@if` (`HasChartData` decide o bloco/FAB), em vez de um gate único que exigia as 6 listas de resumo preenchidas — uma lista vazia (ex.: `CategoriaMedia` num `.bak` sem registos) escondia todos os gráficos.
- **Memória:** o SQL Server 2022 precisa de ~2 GB. Com o Docker Desktop/WSL2 abaixo disso o contentor `sql` sai com **137 (OOM)** e o `db-init` falha depois com `Login failed for user 'sa'`; nesse caso aumentar a memória do WSL2 antes de `docker compose up`.
- O `RESTORE` corre no processo do SQL Server, por isso a pasta dos `.bak` esta montada em `/backup` **no servico `sql`** (e tambem no `db-init`, que verifica o ficheiro). O `.env` versionado define `SQL_SA_PASSWORD`; **nao terminar a senha com `;`** (o `;` e o separador da connection string: fica `Password=...;;` e o login `sa` falha). Depois de mudar a senha e preciso recriar o volume: `docker compose down -v && docker compose up -d`.
- `BaseUrl` do Blazor é `http://webapi:5000` — **sem** `/api`, que o código acrescenta (`Program.cs` + typed clients); incluir `/api` duplica o segmento. A connection string vai por `ConnectionStrings__SqlServerCon` (não `SQLCONNECTIONSTRING`) com autenticação SQL `sa`; o Serilog usa `Serilog__WriteTo__0__Args__connectionString`.
- **O Docker requer um `.bak`:** o `db-init` restaura o `Publicacoes_Prod` a partir de `Web.Blazor/wwwroot/Files/Backup/Database/` (montado como `/backup` no serviço `sql`, default `28102026_123256.Bak`). Sem o ficheiro, `db-init` sai com erro e a stack não arranca — não há fallback com script de schema. O `.env` versionado define `SQL_SA_PASSWORD`; **não terminar a senha com `;`**.
- **Ollama nos contentores:** o servico `ollama` corre o **motor**, nao modelos. Os ficheiros vivem no volume `ollama-data` (`/root/.ollama`) e um volume novo arranca **vazio** — a imagem nao traz modelos e o store do host (`~/.ollama`) nao e visivel no contentor (alem disso o Ollama do Windows escuta em `127.0.0.1:11434`, inacessivel de dentro da rede do compose). O `db-init` forca `ModelBaseUrl=http://ollama:11434`, e **`Ollama:BaseUrl`/`Ollama__BaseUrl` so define o `BaseAddress` do `OllamaSharedClient`**: todas as chamadas (`OllamaBaseClient`, `OllamaChatService`, `OllamaModelsService`) constroem URI absoluto a partir do `ModelBaseUrl` da BD, por isso a variavel do compose, sozinha, nao redireciona nada. **`AiModelName` e estado do utilizador, nao um default do projeto:** e o modelo escolhido em App Settings, herdado do `.bak` (`Qwen3:1.7B` no `28102026_123256.Bak`) e alteravel a qualquer momento; tem de nomear um modelo instalado nessa instancia, senao todas as chamadas locais dao `404 model not found`. A app lista **instalados** (`/api/tags`), nunca `ollama ps`. O fluxo cloud/OpenRouter nao depende disto. Guia para utilizadores: `Web.Blazor/docs/ollama-docker-setup.md`; pull manual: `docker compose exec ollama ollama pull qwen3:1.7b`.
- **Fragilidade conhecida (settings + Ollama em baixo):** `AppSettings.razor.cs`/`AppSettings2.razor.cs` carregam `AIModelsSrvice.GetAllAsync()` e `AppSettingsService.GetSettingsAsync()` no **mesmo** `try` com `catch { settings = new(); }`; se o Ollama estiver inacessivel a lista lanca, a pagina mostra `ModelBaseUrl`/`AiModelName` vazios e gravar apaga-os. E `AIModelsApiWrapper` usa o timeout HTTP por omissao (100 s), pelo que um pull grande pela UI (`LookupTables → AI Models`) aborta a meio (o cliente da WebApi tem 10 min).
- `Web.Blazor\wwwroot\Files` (1,3 GB) está no `.dockerignore` e é montado do host em `/app/wwwroot/Files` nos dois serviços. **Na verdade só os assets da aplicação (`Pictures\Application|Authores|BookHardCovers`) são versionados**: os `Uploads\` e `Backup\` (dados do utilizador, ~740 MB + `PdfsAndCovers.zip` 493 MB) estão no `.gitignore`, pelo que `wwwroot\Files` **não** é a fonte de verdade completa da aplicação num clone novo — um destino limpo fica sem os dados do utilizador (mas não sem os ícones). O deploy IIS faz `robocopy /MIR` integral da pasta e não exclui subpastas; `/XD wwwroot\Files` não protege contra o purge do `/MIR` (verificado em sandbox) — não confiar nele para preservar dados.
- `docker/nuget.config` restaura só de nuget.org (o `nuget.config` da raiz já aponta apenas para nuget.org — a nota antiga de feed Syncfusion com chave placeholder está desatualizada). Os Dockerfiles publicam framework-dependent (`aspnet:10.0`), sem self-contained.
- **Limitacao conhecida:** `System.Drawing.Common` e Windows-only em .NET 6+. Os caminhos que o usam (`Web.Blazor/Services/DocumentHelpers/PdfHelper.cs`, `Pages/BaseComponents/MediaBase.razor.cs`, `PublicacoesBase.razor.cs`, `MediaPlayer.cs`) lancam `PlatformNotSupportedException` nos contentores Linux (redimensionar/gerar imagens e alguns PDFs). Consultar/navegar e o CRUD normal funcionam; a app continua pensada para Windows/IIS.

## AI Integration

**Two-layer architecture: OpenRouter (cloud) is the PRIMARY provider; Ollama (local) is the FALLBACK.** For translate, media notes/metadata/edition-year, author-books, book-summary and author-profile, the Blazor UI first calls the `*-cloud` WebApi endpoints (OpenRouter); when they return null/503 (offline, no API key, 429, HTTP/parse error), it falls back to the local Ollama endpoints (`/api/ai/translate`, `/api/ai/media-notes`, `/api/ai/media-metadata`, `/api/ai/author-books`, `/api/ai/book-summary|book-summary-only`, `/api/ai/author-profile`). Every Cloud service (`CloudTranslateService`, `CloudMediaService`, `CloudBookSummaryService`, `CloudAuthorBooksService`, `CloudAuthorProfileService`, `OpenRouterChatService`) is designed to return null on failure so the caller falls back to Ollama. The "Pesquisar Books Online/AI" flow (`Web.Blazor/Pages/Publications/GoogleBooksApiSearch.razor.cs`) follows: Google Books API first (query with **bare** `intitle:...`/`inauthor:...` operators — the quoted phrase syntax returns zero items); when a found volume lacks `volumeInfo.description`, its `searchInfo.textSnippet` is used as `Resumo` (then MyMemory-translated) before any AI; AI (`book-summary-cloud`→`book-summary`, OpenRouter→Ollama) is invoked only when Google Books returns no items at all, or items without both `description` and `textSnippet`.

- **Local (Ollama) services** (`MediaOrganizerApp.WebApi/Services/Ollama*Service.cs`) talk to the base address of the `"OllamaSharedClient"` named client in `Program.cs`, which reads the optional `Ollama:BaseUrl` config key and defaults to `http://localhost:11434` (Docker sets `Ollama__BaseUrl=http://ollama:11434`). The active local model (`ModelBaseUrl` + `AiModelName`) is stored in the DB (`ApplicationSettings` via `AiSettingsProvider`, 60s cache). `Web.Blazor` also connects to Ollama directly via Microsoft.Extensions.AI (`IChatClient`/`OllamaApiClient`) for the `AiChat` page.
- **`Ai:Provider` config key only switches the LOCAL fallback `IAiAuthorProfileService`** in `ServiceRegistration.cs`: `Ollama` → `OllamaAuthorProfileService`, anything else → OpenAI-SDK `AiAuthorProfileService` (pointed at the DB `ModelBaseUrl`). Author-profile itself is cloud-first (see below): `/api/ai/author-profile-cloud` (OpenRouter) is called first and falls back to the local `/api/ai/author-profile`. It does NOT control the other AI services — those are wired in `Program.cs` (local = Ollama, cloud = OpenRouter).
- **OpenRouter / cloud-chat settings live in the DB** (keys in `Application/Configurations/CloudChatSettingsKeys.cs`): `CloudChat:OpenRouterApiKey`, `CloudChat:DefaultModel` (default `openrouter/free`), `CloudChat:EnableReasoning`, `CloudChat:AllowPaidModels`, `CloudChat:FreeDailyCap`, `CloudChat:AuthorBooksUseCloud`, `CloudChat:ExtractionModels`, `CloudChat:EverPurchasedCredits` (snapshot interno, não editar). Configured via the **single "IA" area of the admin settings pages** (see below; admin-only: API key, reasoning/paid-models/author-books toggles, model picker from the live catalog, free-daily cap, usage cards). `CloudChat:EnableReasoning` is COMMON to both chats (OpenRouter + local Ollama) and therefore sits in the "Definições comuns" IA sub-section — not in the OpenRouter one.

**Settings pages (admin):** `AppSettings.razor` (`/admin/appsettings`) is the ORIGINAL page (footer link `SidebarData.cs:71` points here). `AppSettings2.razor` (`/admin/appsettings2`, same folder) is the REFACTORED version of the same settings screen — Dribbble-inspired layout with a custom icon sidebar + content cards on the right, dark-theme tokenized (`var(--app-*)`), no `SfTreeView`. It is reachable only by direct URL (not linked in the sidebar). Keep both in sync when settings change; new resx keys for its section labels live in `App.resx`/`App.en.resx`/`App.fr.resx`/`App.es.resx`. **Both pages group ALL AI settings under a single "IA" area** (resx `TituloGrupoIA`) with three sub-sections: **"Definições comuns"** (`TituloIAComum`, shared Ollama+OpenRouter: the `CloudChatEnableReasoning` toggle + `CloudChatEnableReasoningHint`), **"OpenRouter"** (`TituloIAOpenRouter` = old "Cloud Chat" tab/leaf: API key, model picker, paid/author-books toggles, free-cap + usage cards), and **"Ollama (local)"** (`TituloIAOllama` = old "IA Local": `ApiKey`/`ModelBaseUrl`/`AiModelName`). In `AppSettings2` the IA sidebar group has leaves `iacomum`/`iaopenrouter`/`iaollama`; in `AppSettings` it's a single tab with the three sections stacked, and the old "OpenRouter ( Chat)" tab / "Cloud Chat" sidebar group and the "IA Local" leaf no longer exist. **Lookup tables admin:** `ManageLookupTables.razor` (`/admin/managelookuptables`) is the ORIGINAL tabbed page (7 `SfTab` tabs embedding the self-contained components from `Web.Blazor/Pages/LookupTables/`). `ManageLookupTablesNew.razor` (`/admin/managelookuptables-new`, same folder) is a REFACTORED version of the same screen using the AppSettings2 template — icon sidebar with collapsible groups ("Publicações", "Média", "IA") + content card showing the selected lookup component; reuses the exact same `LookupTables` components (no logic duplication), dark-theme tokenized (`var(--app-*)`). Reachable only by direct URL (not linked in the sidebar). Keep both in sync; group/format labels use existing resx keys plus `TituloGrupoPublicacoes`/`TituloGrupoMedia`/`TituloGrupoIA`/`frmFormatosMedia` in the four `App*.resx`.

**Ajuda (manual do utilizador):** `Web.Blazor/Components/Help/HelpDialog.razor` (+ `.razor.cs`) is the modal dialog that displays the end-user manual matching the current UI language: `Web.Blazor/docs/Help.md` (Portuguese/default), `Help.en.md`, `Help.fr.md` or `Help.es.md`. It is opened by the help button in the top bar of `MainLayout.razor` (`_helpVisible` + `@bind-Visible`; the dialog itself is reusable by any page through `Visible`/`VisibleChanged`). The Markdown is rendered with Markdig (`UseAdvancedExtensions`) and sanitized with `HtmlSanitizer` (same pattern as the prompt editor README), inside an `SfDialog` whose body scrolls (`max-height: 78vh`) and uses only `var(--app-*)` tokens. The localized file is read from disk **on every open** (no cache), looking in `IWebHostEnvironment.ContentRootPath` and `AppContext.BaseDirectory`, walking up to 6 parent folders as fallback; an unavailable/unsupported translation falls back to `Help.md`. `Web.Blazor.csproj` copies `docs\Help*.md` to output/publish, so editing the manual needs no rebuild. Title = resx `btnHelp`; load failures use `HelpFileNotFound`/`HelpFileLoadError` in the four `App*.resx`. **Internal TOC anchors:** `HtmlSanitizer` percent-encodes fragments while Markdig keeps heading ids in raw UTF-8, so `RenderMarkdown` restores decoded fragments (`NormalizeFragmentHrefs`) and `wwwroot/js/help-dialog.js` (loaded by `App.razor`, NOT a `<script>` inside the component — Blazor does not execute those) handles the click in the capture phase (ahead of Blazor's router), decodes the fragment and scrolls the `.help-content` container itself. The "back to top" button (`.help-scroll-top`, resx key `HelpScrollToTop`) is a sibling of the scroll container inside `.help-body` — inside `.help-content` it would scroll away with the text — and the same JS shows it past ~240px of scroll and scrolls the container back to the start; it is deliberately not an `SfFab` (its `FabPosition` anchors to the viewport/target and gets clipped by the modal).
- **Free vs paid models:** the `AllowPaidModels` toggle MUST be honoured server-side. `OpenRouterCatalogService.GetFreeModelsAsync` exposes free models only unless the toggle is on; `CloudChatSettingsKeys.ApplyPaidModelGate` downgrades a paid recommended model to its `:free` variant (or `openrouter/free`). All cloud services must pass the resolved model through the gate before sweeping candidates (`BuildCandidateModelsAsync`): translate, media-notes, media-metadata, edition-year, book-summary and author-profile use `FreeModelsAsync` (live catalog) when the toggle is off; author-books likewise. Free tier usage is **counted and ENFORCED** via `CloudChatUsageService` (`CloudChat:FreeUsage:yyyyMMdd`, default cap 50/day without credits, 1000/day with credits, overridable with `CloudChat:FreeDailyCap`). Every free-model call first checks `ICloudChatUsageService.GetFreeRequestsRemainingAsync` (cap minus today's counter, resolved without network: `FreeDailyCap` override → `CloudChat:EverPurchasedCredits` snapshot persisted by `GetUsageAsync` → default 50); when 0, the cloud services (`CloudTranslate/Media/BookSummary/AuthorBooks/AuthorProfile`) return null so the caller falls back to Ollama, and `OpenRouterChatService` throws a friendly `CloudProviderTransientException` (cloud chat has no local fallback).
- **Cloud chat** (`Web.Blazor/Pages/AI/OpenRouterChat.razor` → `/api/cloud-chat/stream` → `OpenRouterChatService`) streams from OpenRouter only (no Ollama fallback; on 404 it retries `openrouter/free`, on reasoning-unsupported it retries without reasoning). When the effective model is the router `openrouter/free` and a candidate ends without producing text, `OpenRouterChatService` auto-sweeps to the next candidate (`BuildChatCandidatesAsync`): paid recommended prefixes when `AllowPaidModels` is on, otherwise the LIVE free catalog (recommended ones first, max 12) — freely-chosen free/paid models and HTTP/404/429 failures are never swept. Local chat (`Chat.razor` → `/api/ai/chat` → `OllamaChatService`) is a local-only Ollama page (`/ai/chat`, exception to cloud-first). **Reasoning display:** with the `CloudChat:EnableReasoning` toggle ON, both chats show the model's reasoning as a collapsible "💭 Raciocínio" block per message (collapsed by default, including while streaming — the user expands/collapses it manually per message, and the choice is respected; persisted in conversation history). OpenRouter reasoning arrives via `chunk.Reasoning` (`ChatChunkParser` parses `reasoning`/`reasoning_content`); the local chat streams NDJSON `AiChatChunk` (`Text` + `Reasoning`) from `/api/ai/chat` and `OllamaChatService` surfaces Ollama `message.thinking` **or** `message.reasoning_content` as reasoning when the same toggle is ON — otherwise thinking is dropped. Some thinking models (notably Qwen3) stream the block INLINE inside `content` wrapped in `<think>`/`</think>` (or ` thinking`/` response`) instead of a `thinking` field; `OllamaChatService` also extracts that inline block across chunks (`ProcessInlineThinking` + per-request `pendingInlineReasoning`/`inInlineThinking`/`inlineMarkerCarry` state: a marker split across NDJSON chunks is held back until it is complete, an orphan `</think>`/` response` close marker is dropped instead of leaking into the answer, and an unclosed block is flushed at `done:true` or end-of-stream) — with the toggle ON it becomes `Reasoning`, with it OFF the whole block is discarded so markers never leak into the answer. Field-based `thinking`/`reasoning_content` still wins over the inline fallback, and an unclosed inline block is flushed at `done:true`. For models that send reasoning only in the final message, `OllamaChatService` re-parses the `done:true` line for reasoning; thinking-capable models (`SupportsThinking`: qwen3\*, deepseek-r1\*, qwq\*, \*:reasoning) get an explicit `think` payload field (true/false per toggle), common models omit it (Ollama rejects `think` with 400 otherwise). Durante a tradução aparece um botão **Cancelar** (`CancelTranslate()`) que aborta a request: o UI para **imediatamente**, sem esperar pelo provider (o Ollama local pode continuar a inferir). O botão **Traduzir** fica sempre disponível à esquerda; ao cancelar, a mensagem `TituloTraducaoCancelada` ("Cancelado pelo utilizador" / "Cancelled by the user" / "Annulé par l'utilisateur" / "Cancelado por el usuario") aparece **à direita**, no slot do `Confidence` (que é `null` nesse estado, por isso nunca colidem) — insister em traduzir apaga a mensagem (`Translate()` faz `IsCancelled = false`); `Confirmar` permanece desativado por não haver texto traduzido. Fechar o diálogo (`OnExit`), disposing o componente e `Visible` passar a false cancelam **em silêncio**, para uma resposta tardia não sobrescrever o campo (ex. a bio do autor); `Translate()` ainda protege cada escrita com `if (cts.IsCancellationRequested || !ReferenceEquals(_cts, cts)) return;`. O cancelamento propaga ponta-a-ponta (abortar o `HttpClient` da Blazor faz o ASP.NET Core cancelar o token do controller → `CloudTranslateService`/`OllamaBaseClient`, cujo CTS ligado distingue timeout de cancelamento), e **ambos os providers rethrowam** `OperationCanceledException` em vez de a reportarem como falha de IA (`OllamaTranslateService.TranslateAsync`, `TranslateClientService.TranslateLocalAsync`; `TranslateAsync` também faz `ThrowIfCancellationRequested` antes do fallback local, para cancelar no cloud não disparar o Ollama). `TranslateClientService` está registado com `Timeout = 6 min` (era 100 s por omissão) para ultrapassar os 300 s de `OllamaBaseClient.ExecuteGenerateAsync` — é um teto, nunca uma espera. - **Provider/modelo da tradução (chip no diálogo):** o sweep de até 12 candidatos (`CloudTranslateService.BuildCandidateModelsAsync`) e o fallback silencioso para o Ollama tornam o modelo **imprevisível por construção** — o `CloudChat:DefaultModel` raramente é o que respondeu. Por isso o `TranslateResponseDto` ganhou `Provider`/`Model`, e o `ProgressUpdateDto` idem (`Application/DTOs/AI/`) para o modelo **em voo**. O chip aparece **por baixo do botão Traduzir** (nunca no slot direito, que fica com a nota de cancelamento ou o `Confidence` — os ids de modelo são longos e sobrepunham texto) em dois estados: **sucesso** (`⊘ OpenRouter · llama-3.3-70b`, authority: o DTO) e **cancelado** (mesmo chip, com "Modelo em tentativa" no `title`) — neste caso o modelo vem **do canal de progresso**, porque um cancelamento aborta a request e o servidor nunca devolve body. Enquanto a tradução decorre o chip **não** aparece: a mensagem de progresso já nomeia o modelo (`AIProcessingCloudTrying` = "A tentar com OpenRouter ({0})...", que só agora dispara, já que `CloudTranslateService` passou a publicar `cloud_try`/`cloud_success`/`cloud_failed`/`cloud_empty` com `Provider`/`Model`). `CloudTranslateService.TryRawCompletionAsync` devolve o modelo **servido** (`ExtractServedModel` do body) para reportar o modelo real quando passa pelo router `openrouter/free` (igual ao `RealModelName` do `OpenRouterChat`); sem `model` no body, cai para o candidato pedido, que o UI mostra como `CloudChatAutomaticModel` ("Automático"). Ambos os serviços **carimbam** Provider/Model por cima do DTO desserializado — a saída do modelo nunca é fonte de verdade. `AiController.RecordUsageAsync` ganhou `modelo` e `Translate`/`TranslateCloud` passam `resp.Model`, preenchendo a coluna `AIUsageLog.Modelo` (que existia e nunca era escrita; `AiUsageRecorderService` trunca a 128 chars).

## Conventions

- **ORM mix**: Dapper for most queries, EF Core for Identity and some persistence. Raw SQL strings are common in repositories (e.g., `StringBuilder`-based query building).
- **Localization**: Default culture is `pt` (Portuguese). Supported: en, fr, pt, es. Resources in `Web.Blazor/Resources/`.
- **Syncfusion**: UI components use Syncfusion Blazor suite. Requires a license key (hardcoded in `Web.Blazor/Program.cs`).
- **Reports**: RDLC templates in `Reports_RDLC/` directories, shipped with `MediaOrganizerApp.WebApi`. The WebApi renders them locally via `ReportViewerCore.NETCore` (`ReportController.cs`).
- **Service registration**: register services that depend on `HttpClient` via `AddHttpClient` in `ServiceRegistration.cs` (`AddServicesInfrastructure`) — never directly in `Program.cs`; persistence services go in `AddPersistenceInfrastructure`. Blazor API clients are registered via `AddHttpClient` in `Web.Blazor`'s `ServiceRegistration`. UI components should not call API endpoints directly — use typed API client wrappers reading `BaseUrl` and the `ApiKey` header from configuration.
- **External service credentials live in the DB, not in code**: there is no `Keys.cs` anymore. LastFm, GoogleBooks, IMDb and YouTube (`YouTubeApiKey`/`YouTubeClientId`/`YouTubeClientSecret`/`YouTubeApplicationName`) are columns of `dbo.ApplicationSettings`, edited in the "Serviços" section of `AppSettings.razor`/`AppSettings2.razor` and written through `usp_AppSettings_Update` (`scripts/AddYouTubeSettings.sql` adds the YouTube ones; `GetSettingsAsync` is `SELECT TOP 1 *` so new columns map automatically). Consumers read them at runtime: `YouTubeSubscriptionService` via `IAppSettingsRepository`, `GetYoutubeVideoMetadata`/`YoutubeService` (Web.Blazor) via `IAppSettingsService` (absolute `BaseUrl`). Never inject the bare `HttpClient` for this — the generic `AddHttpClient()` registration has **no `BaseAddress`**, so relative URLs throw `HttpClient.PrepareRequestMessage`.
- **SignalR**: all SignalR/Hub work lives in the service layer, not the UI.
- **No CI/CD config** in use: `.github/workflows/*.yml` exist but are stale (reference non-existent projects). No pre-commit hooks.
- **No linting/formatting enforcement** beyond the single `.editorconfig` rule (CA1051 suppressed).

## Gotchas

- `Web.Blazor.csproj` explicitly disables `GenerateAssemblyInfo` and `GenerateTargetFrameworkAttribute` to avoid duplicates — don't re-enable without checking.
- The `Web.Blazor` project excludes `Services/ApiRelated/**` from compilation — dead code kept for reference.
- All projects in the solution target **net10.0** (only `PromptEditor` is `net10.0-windows` and is not part of any solution).
- `nuget.config` includes a Syncfusion NuGet source with a placeholder API key (`<your-api-key>`). If restore fails, check this.
- Serilog writes to SQL Server (`AppLogs` table) — `autoCreateSqlTable: true` in config. The table is auto-created on first write.
- AI Ollama client uses `SocketsHttpHandler` with aggressive keepalive to handle long-running LLM inference requests (up to 10-15 minute timeouts).
- **Running the app locks `Web.Blazor.dll`** (VS + IIS Express). `dotnet build` will fail with `MSB3027/MSB3021` on the copy step while the app is running — the compilation itself succeeds; just stop the app or build a single project to verify. Do not mistake these for code errors.
